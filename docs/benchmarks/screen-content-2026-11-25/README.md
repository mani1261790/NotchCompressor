# 画面内容の圧縮比較 — 2026-11-25

## 素材と測定範囲

ユーザーの動画提出は不要。`scripts/make-quality-fixture.py`で独自に生成した1920×1080・60fps・12秒の素材を使用。日本語／英語の10〜32px文字、色文字、1〜2px線、スクロール、動く図形、毎秒の点滅とビープを含む。元動画は25,639,320 bytes。H.264 VideoToolboxの40 Mbps指定とAAC 192 kbpsで作成した**非可逆素材**であり、画面収録そのものではない。生成前PNGを原本動画の画質と取り違えない。

このMac（arm64、macOS 27.3）、同梱FFmpeg 9.0.1で6方式×3回を固定シードで順序を混ぜて比較した。電源・温度・他プロセス負荷は記録していないため、短時間の同一セッション内の参考値として扱う。全方式ハードウェア必須、元fps維持、音声コピー。ビットレート方式は7,464,960 bps指定。総時間には入力解析・圧縮・出力解析・全体デコード検証・音声パケット照合を含め、素材コピーと整合性ハッシュ計算は除く。アプリ全体の所要時間ではない。

## 測定結果（3回の中央値）

| 方式 | 出力 MB（10進） | 削減率 | 総時間 秒 |
|---|---:|---:|---:|
| hevc-bitrate | 10.84 | 57.7% | 5.29 |
| hevc-fast | 11.44 | 55.4% | 3.90 |
| h264-bitrate | 11.18 | 56.4% | 4.77 |
| hevc-quality-50 | 4.07 | 84.1% | 4.95 |
| hevc-quality-65 | 6.35 | 75.3% | 5.14 |
| hevc-quality-80 | 9.90 | 61.4% | 5.38 |

18回すべてデコード検証成功。音声パケットのハッシュとPTSが入力に一致し、比較後も元動画のSHA-256は一致。各方式の1回目について、映像720フレームすべての表示時刻も入力に完全一致した。これは相対的なタイミング保持の証拠であり、耳と目による同期確認の代わりとはしない。

## 画像の確認と暫定判断

各方式の1回目をデコードし、1.0秒の静止文字・細線、4.5秒と10.5秒のスクロール文字を、拡縮しない同座標の切り抜きで比較した。画像抽出は開発用Homebrew FFmpegを使用（同梱版にはPNGエンコーダがない）。

- 品質50: 小さい黒文字と色文字の輪郭ににじみ・周辺ノイズが見え、スクロール中の色文字も劣化。容量だけを根拠に既定採用しない。
- 品質65: 品質50より輪郭が改善。ただし小さい文字や細線周辺には差が残る。容量重視の追加候補として継続評価。
- 品質80、現行HEVCビットレート、速度優先、H.264ビットレート: 確認した切り抜きでは文字を読める状態を保つ。全場面・全動画で同品質という判定ではない。
- 速度優先は現行HEVC比で総時間約26%短縮、出力約5.5%増。この素材での結果であり、画質同等や常時高速を保証しない。

既定は現行HEVCハードウェア／標準を維持する。今回の静止比較だけでは、品質指定や速度優先への既定変更を正当化しない。現行方式が最適という結論でもない。

## 全フレームの同期検査

`scripts/check-fixture-timing.py`で6方式それぞれの1回目を再検査した。12回の白い点滅は入力・出力で同一フレームに存在し、入力のビープ開始は10ms単位の検出で0〜11秒の毎秒の点滅と一致。各出力の映像PTS720個、音声パケットPTS、デコード音声のSHA-256・サンプル数も入力と一致した。結果は`sync-check.json`。AACの端数を含む576,512サンプルを比較しており、12秒×48kHzへの切り詰めはしていない。

検査自体の確認として、音声を200ms遅らせて再多重化した素材を作成。同じ検査が音声時刻・音声内容・サンプル数の不一致で終了コード1となり、誤って合格にしないことを確認した（`sync-negative.json`）。これは生成素材用の検査で、音声を再圧縮した一般動画の品質検査ではない。連続再生時の目視・聴取を実施したとは扱わない。

```sh
python3 scripts/check-fixture-timing.py .local-work/quality-comparison/input.mov .local-work/quality-comparison/*-1.mov --output .local-work/quality-comparison/sync-check.json
```

## ブラウザでの再生確認

ローカルの比較ページで元動画と現行HEVCの1回目を実際に再生し、12.00秒の終端まで進むことを確認。ブラウザのVideoPlaybackQuality表示は元動画で4/720、HEVCで0/720のドロップを報告した。この数値はプレーヤー・表示環境の値で、エンコードされたファイルのフレーム欠落とは区別する。スクロール場面の画像を確認したが、途中でブラウザ幅が狭くなり画面全体の同条件比較にはなっていない。音を聴取した証拠や、全方式の動きの主観評価には使わない。

## 品質指定の対応条件

[FFmpeg 9.0の公式ソース](https://www.ffmpeg.org/doxygen/9.0/videotoolboxenc_8c_source.html)と同梱版の`.build/vendor/ffmpeg-9.0.1/libavcodec/videotoolboxenc.c`を確認した。`-q:v`はMacのARM64ビルドだけで許可され、非対応環境ではエラーとなる。値は100を基準にVideoToolboxのQualityプロパティへ変換される。Intel版やRosetta下へこのMacの結果を一般化しない。x264/x265のCRFと同じ尺度ではなく、目標容量や文字の読みやすさを保証する数値でもない。

今回確認したのはこのMac／同梱版での実動作であり、OS・機種全組合せの保証ではない。アプリへ追加する場合はエンコーダの対応確認と、失敗時の案内または明示的な代替処理が必要。現段階では既定に採用しない。
