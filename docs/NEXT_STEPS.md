# 次の改善計画（2026-11-25）

## 目的と前提

画面収録を、元データを守りながら、文字と動きが用途に十分な品質で小さくする。現在のHEVCハードウェア圧縮を比較の基準に残す。コーデック変更や速度優先の既定化は比較結果を見て決める。全計画を対象とするCodex Goalを実行中。段階ごとにIssueで追跡し、検証後に次へ進む。既存#7・#28は画質・速度評価、#6はログイン等の実機確認、#19・#21は配布・更新検証に関連付け、重複作業を避ける。

## 1. 容量が減らなければ元動画を保持する（#29）

Goal: 出力が元以上の容量なら置き換えず、正常な「削減なし」として処理を終了する。

- 成功して置換／削減なしで原本保持／失敗を結果として区別する。実際の保存サイズと候補出力サイズを混同しない。
- 一時出力は片付け、キューからは完了項目として除外。通知・直近結果・履歴には「容量が減らなかったため元動画を保持」と表示する。
- 元ファイル変更検知・キャンセル・置換の排他を維持。既存の成功出力の全体検証を高速化のために削らない。
- 完了条件: 同容量・増加・削減、外部変更・停止・取消の各経路で元データと結果表示が正しい。旧履歴が読み込める。

## 2. スリープ復帰を安全に扱う（#30）

Goal: 実行中にスリープしても原本を壊さず、復帰後に処理継続または明確な要確認状態へ移る。

- 自動スリープ抑止は維持。ユーザーが明示的にスリープさせた操作は尊重する。
- OSによる中断とユーザーの一時停止を別管理し、手動停止したタスクを自動再開しない。
- スリープ通知と変換完了・置換の競合、復帰通知の重複、待機タスクの開始を検討する。
- 復帰後の子プロセスと保存先の状態を確認。外付けディスク切断・容量不足・エンコーダ失敗時は原本保持、理由と再試行を提示する。
- 途中再開は同一プロセスが保持できた場合に限る。終了済みプロセスやアプリ再起動をまたぐチェックポイント再開は今回対象外。
- 完了条件: 状態遷移テストに加え、実Macで圧縮中・検証中・手動一時停止中のスリープ／復帰を確認。ロック・消灯・ディスク切断も区別して記録する。実機を眠らせる試験はユーザーの利用を妨げない時間に行う。

## 3. フレームレートと設定説明を整理する（#31）

Goal: fpsの削減を明示的に選べ、ハードウェア使用と速度優先の意味が伝わる。

- 新規設定の既定は「元のフレームレートを維持」を候補とし、「最大30fps」を選択可能にする。変更前後の容量・速度を段階4で評価する。
- 投入済みタスクは投入時の設定を保持。旧履歴・旧設定には移行方針を定義し、実行待ちタスクの挙動を黙って変更しない。
- fps維持時はビットレート計算と検証条件も見直す。可変fps・時間情報・音ズレを確認する。
- 「標準・速度優先の両方でハードウェア圧縮」「速度優先は画質と圧縮効率に影響」を画面上で明示する。
- 完了条件: 24/30/60fps、可変fpsの入力で選択どおりのタイミングを維持し、保持トラックと音声同期を確認する。

## 4. 実収録で比較し、品質・容量の調整方法を決める

Goal: 代表的な画面収録の測定と目視評価に基づき、既定設定を選ぶ。

- 許可された動画のコピーだけを使う。静止した資料、小さい文字のコード画面、スクロール、アニメーション、映像混在、無音声を含める。個人情報を含む動画は公開・リポジトリ登録しない。
- 現行HEVCのビットレート指定、HEVCの品質指定、H.264ハードウェアを比較。fps等の条件を揃え、標準／速度優先は別の比較軸にする。
- 品質指定の対応OS・機種と実エンコーダの挙動を調べてから試験実装する。品質指定と内容解析による自動選択は別物として扱う。
- 解析・変換・検証ごとの時間、総時間、出力容量、小さい文字・色文字・動き・音声同期を記録する。画質指標だけで可読性を合格にしない。
- 比較は同じ入力・Mac・電源条件で複数回実施。異なるコーデックでは同程度の見た目の品質で容量と速度を比較する。
- 内容を事前解析する方式は、解析コストを含めた総時間と効果を見て採否を判断。自動判定を先に作り込まない。
- CPUのx265やAV1は、上記で必要な品質・容量が得られない場合の追加比較候補。既定採用は約束しない。
- 完了条件: 設定ごとの比較表と実収録の目視結果があり、既定値・用途別の選択肢・不採用理由を説明できる。実素材が未提供なら合成試験までに限定し、最適性を断言しない。

## 5. 日本語・英語を一貫して表示する（#32）

Goal: アプリが選んだ言語で、通常操作から失敗・復元まで表示を統一する。

- 文言を翻訳リソースへ集約し、日本語と英語を用意。原則macOSのアプリごとの優先言語に従い、未対応言語は英語へ統一してフォールバックする。場当たり的な文言単位の言語切替はしない。
- 対象はノッチの3領域、キュー、設定、メニューバー、ツールチップ、アクセシビリティラベル、確認ダイアログ、通知、エラー、診断画面、更新案内。件数の単複・数値・容量・時間の書式も揃える。
- 現在はOS等のlocalizedDescriptionを日本語文へ連結する箇所がある。利用者向け本文は構造化したエラー理由から翻訳し、生のエラーやログは明示的な技術詳細へ分離する。
- 履歴へ翻訳済み文章だけを保存すると言語変更後に混在する。結果・理由コードと値を保存し、表示時に翻訳する。既存履歴は原文の意味を捏造せず、安全な共通案内と必要時の旧記録詳細へ移行する。
- Sparkleなど依存UIの言語選択も実配布アプリで確認する。macOS自身のシステムダイアログはOSが制御する範囲として、アプリ所有の文言と区別する。
- DMGの背景・案内は一枚に日英を混在させず、言語別DMG等の配布方法を決める。README・リリース案内も日英の文書を分け、言語切替リンクを設ける。法的文書の原文やユーザーのファイル名は翻訳対象外。
- 完了条件: ja/enそれぞれで通常操作・容量不足・削減なし・失敗・履歴復元・更新案内を確認。翻訳キーの欠落を検査し、英語UIに日本語の固定文言が出ず、日本語UIにも未翻訳の英語操作文言が出ない。長い英語のボタン・ノッチ・通知が切れないことも実機確認する。

## 6. 次版を配布し、Sparkle更新を通しで検証する

Goal: 公開済みalpha.2から次版へ、安全に更新できることを確認する。

- 段階1〜3と5を次の安全性・言語対応版、段階4の既定変更を評価後の版に分けられる。段階5は段階4の実素材待ちでも進められる。未評価の圧縮方式を安全性修正と一緒に既定化しない。
- 実メディア試験・CI・署名・公証・Gatekeeper・匿名ダウンロード照合を実施する。
- alpha.2から更新確認→取得→置換→再起動を実機確認し、設定・キューが保持されることを確認する。処理中・一時停止中は更新で勝手に再起動しない。
- 残っているFinderドロップ、通知、ログイン起動の確認もこの段階へ集約する。画面操作環境が使えなければ、未確認として残し、確認済みにしない。
- 完了条件: 配布検証と実更新の結果を記録し、GitHub Releaseと署名済みフィードを順番に公開する。


## 7. 動画以外の対応を設計する（上記の改善後）

Goal: 実利用の優先度と、形式ごとの安全な圧縮・保存方法を決める。現時点では候補の整理であり、全形式の対応を約束しない。

- 候補は静止画像、音声単体、PDF、一般ファイルのアーカイブ。画像・音声の再圧縮とZIP化は目的が異なるため、別機能として扱う。
- 候補順は画像→音声を起点に実需要で決める。PDFは文字・リンク・注釈等の保持が必要で、別途評価する。
- 透過・アニメーション・色・メタデータ、音声のタグやチャンネル等について、保持要件と非対応条件を形式ごとに定義する。
- キュー、順序、容量不足、通知、言語対応、安全な一時出力と置換を共用できる構成を検討する。各形式の検証処理は分け、現段階で不要な汎用化は行わない。
- 動画の「画質のみ／音質のみ／両方」をそのまま流用しない。画像・音声や異種ファイル混在ドロップ時のノッチ領域と設定を設計する。
- 拡張子・形式が変わる場合、非可逆変換、署名付き文書等では動画と同じ上書き方針を自動適用しない。別名保存や非対応の扱いを設計時に決定する。
- 完了条件: 優先する最初の形式群、保持要件、保存方針、対応外の表示、試験素材と検証方法を定め、実装Issueへ分割する。

## 8. 検証・配布後の製品拡張

ユーザー要望に基づく今後の計画。現行版のスリープ・言語・配布検証を先に終える。この節は実装済みの機能一覧ではなく、着手時に順番にIssueとGoalへ分割する。

1. **設定なしで使える既定動作を整える。** 段階4の実素材評価を根拠に、文字の読みやすさ、滑らかさ、速度、容量のバランスを選ぶ。対応環境ではハードウェア圧縮を優先し、元のfps・解像度を下げる判断は評価で裏付ける。削減できない場合は元を保持する。初回にコーデックや数値の選択を求めず、詳細調整は設定から行えるようにする。所要時間・容量削減・品質・発熱を合わせて評価し、「万能な固定値」を最適と断言しない。
2. **画像、次に音声を追加する。** 段階7の保存・保持要件を満たす小さな形式群から対応する。JPEG/PNG、M4A/MP3/WAV等は調査候補であり対応保証ではない。拡張子だけでなく内容から種類を判定し、混在ドロップでも適切な処理を選ぶ。透過画像、アニメーション、可逆音声の非可逆化などは、無設定で意味や性質を変えない。対応できないものは理由付きでスキップする。
3. **ノッチ／Dynamic Islandへの適応と他アプリとの共存を設計する。** ユーザーの最新指示によりDynamic Island対応を要件へ戻す。[AppleのWidgetKit資料](https://developer.apple.com/documentation/widgetkit/)にはMacのDynamic Islandへの表示が記載されている。対応OS・機種・公開APIを調べ、システムが管理するLive Activitiesと、自前のファイルドロップ領域を区別して実装方法を決める。既存APIのsafeAreaInsetsだけで島の正確な位置・形状を取得できると仮定しない。
   - 待機時はアプリ独自の黒い背景を常時描かない。音楽・時計がオフなら追加の表示を出さず、ファイルが近づいたときだけ受け取り領域を展開する。見えない領域がメニューバーや他アプリのクリックを奪わないようにする。
   - ノッチ／島の位置を展開アニメーションの基準とし、共通の圧縮操作へ広げる。ノッチは上端につながる形、島型は独立した角丸形から始めるなど、開始形状・高さ・余白を機種に合わせる。ノッチなし外部画面の基準位置も定める。
   - ウインドウのドロップ判定領域を動かすとFinderのドラッグ受け取りが不安定になるため、判定領域は先に確保し、描画側をアニメーションさせる。完全透明・非表示のウインドウがドラッグを受け取れるとは仮定せず、実機で確認する。動きを減らす設定にも対応する。
   - 表示位置の選択、メニューバーからの投入、呼び出し方法を検討し、他のノッチアプリの操作を妨げないか確認する。システムの島そのものを任意に変形できることや、他アプリの表示を自動統合できることは前提にしない。
4. **ノッチ部分に任意の音楽・時計表示を追加する。** 表示先は圧縮キュー等のウインドウではなく、画面上部のノッチ周辺とその展開領域。圧縮進捗、時刻、再生中の音楽を小さく並べ、展開時に必要な情報・操作を表示する。カメラ部分に情報が隠れない配置にし、ファイルのドラッグ中は圧縮のドロップ領域を優先する。このMacのNotchBoxなどを参考に、待機時の情報量、展開と収納、音楽操作、時計と複数情報の配置を実機で比較する。時計から試作し、音楽は公開API・権限・対象プレーヤーの対応範囲を調査してから実装する。音楽・時計はそれぞれ任意で有効化でき、初期状態ではオフにする。表示機能を有効化してもキューウインドウを開く必要はない。

各段階の完了条件には、未設定の新規ユーザー、日英表示、アクセシビリティ、複数画面、他のノッチアプリとの競合、元ファイルの保持を含める。表示位置や任意カードの好みは設定可能にするが、圧縮を始めるための必須設定にはしない。

参考アプリの確認状況: NotchBoxは起動・Show Main Windowまで操作できたが、CUA画像は白い表示で内容を取得できず、音楽・時計の実表示は未確認。確認済みの参考デザインとして扱わない。
